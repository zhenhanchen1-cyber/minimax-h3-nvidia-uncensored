# 真机踩坑与前置要求（N 卡 · 2026-10-13 实测更新）

> 这份文档只记**真机上跑起来之后才暴露**的问题，不是"看文档就能猜到"的那种。
> 测试环境：云主机 **RTX 4090 48GB（显存魔改版）×1**，驱动 570.172.08，PyTorch 2.9.1+cu128，
> ComfyUI 0.39.0，Python 3.11.12，系统盘 30G + 数据盘 50G。
> 如果你正准备租一台卡跑，**先花两分钟读完第零、一节**，能省一小时。

## 一、磁盘：50GB 数据盘装不下 balanced 档（实测踩到）

balanced 档的真实体积（实测字节数，不是估算）：

| 文件 | 大小 |
|---|---|
| 融合 Turbo 主模型 `minimax_h3_fused_..._int8_convrot.safetensors` | 21.0 GB |
| 文本编码器 `qwen3vl_32b_h3_ultra_uncensored_heretic_int8_convrot.safetensors` | 26,363,476,151 B ≈ 24.6 GiB |
| 视频 VAE fp16 | 5,207,808,496 B |
| 音频 VAE fp32 | 605,254,808 B |
| 4 步 LoRA / 8 步 LoRA | 各 1,956,192,992 B |
| **合计** | **≈ 48.25 GB** |

云主机常见"系统盘 30~50G + 数据盘 50G"的组合**刚好差一口气**。三种解法，按推荐度排：

1. **扩盘**（最省事）：云平台后台把数据盘扩到 80~100GB。
2. **软链混布**（本次实测采用，不花钱）：
   ```bash
   COMFY_HOME=/root/ComfyUI bash scripts/install.sh    # ComfyUI 装系统盘（约 5GB）
   ln -sfn /hy-tmp/models /root/ComfyUI/models          # 模型整体放数据盘
   ```
   `install.sh` 支持 `COMFY_HOME` 覆盖；且当 `COMFY_HOME` 已存在（例如 models 已是软链）时，
   它会先克隆到临时目录再 `cp -a` 拷入，**不会因为"目标非空"而失败**。
3. **精简档**：文本编码器换更小的量化档 + 删掉 8 步 LoRA（省约 6.5GB），勉强塞进 50GB。

> ⚠️ 按量计费实例**停机不等于保数据**（常见规则：24 小时不启动即清空数据盘）。
> **出片后立刻 scp 拉回本地并校验字节数**，别把成片留在云上。
> 我们上一次就把 5 段素材留在服务器上，结果环境被回收、素材全丢。

## 二、文本编码器：GGUF 路线对 H3 走不通（真机验证，必崩）

- **现象**：`ClipLoaderGGUF` 报
  `TypeError: the JSON object must be str, bytes or bytearray, not NoneType`
- **日志先兆**：`No mmproj file found for '<xxx>.gguf'`
- **根因**：H3 的文本编码器是 **Qwen3-VL（多模态，带视觉塔）**。市面上所有 H3 的 GGUF 文本编码器仓库
  （eraiko / unsloth 实测都确认）**只放了纯文本权重，没有 mmproj 视觉塔文件** → 构建不出 tokenizer
  → `tokenizer_data = None` → `json.loads(None)` 崩。
- **结论**：
  - **GGUF 只适合主模型（diffusion model）**，这条路没问题；
  - **文本编码器必须 safetensors + 官方 `CLIPLoader`**（视觉塔内含），`type` 选 `minimax`；
  - 可用的"去审查"组合：`qwen3vl_32b_h3_ultra_uncensored_heretic_int8_convrot.safetensors`（26.4G）。
- `scripts/download.py` 自 2026-10-13 起**默认只下 safetensors 编码器**，不会再下 GGUF 编码器。
  社区那些"用 GGUF 编码器省显存"的老教程，在 H3 上是**走不通的**。

## 三、SLA 稀疏注意力：驱动 < cu130 必崩（抓到了完整因果链）

报错：`RuntimeError: detect_k_anchor kernel launch failed: CUDA driver version is insufficient for CUDA runtime version`

因果链（真机日志逐条对上）：

1. 启动日志早有预警：`You need pytorch with cu130 or higher` → `comfy_kitchen` 的 CUDA/Triton 后端 `disabled: True`
2. SLA 退回 **eager** 实现，而 eager 是 **O(T²)**：0.98MP / 124 帧需要 **197~611 GiB**，直接爆
3. 崩溃后自动回退 dense，dense 又走 comfy_kitchen 的 INT8 注意力核，同样要新驱动 → **二次崩溃**

**解法**：用本仓库的 **4 个「无SLA版」工作流** —— 把 `H3SLAAttention` 节点摘掉，
模型从 `UNETLoader` 直连 `MiniMax H3 Sigma Shift` 即可正常出片（只是慢一些）。
驱动升级到 cu130+ 之后再换回带 SLA 的版本。

> 因此本仓库 README 里的实测数据全部是**无 SLA 的保守值**，读数时请注意。

## 四、两个已修的脚本 bug（用早期版本会遇到）

1. **`install.sh` 的 `REPO_DIR` 用相对路径计算**
   在 `cd $COMFY_HOME`、`cd custom_nodes` **之后**才用 `BASH_SOURCE[0]` 取值，
   结果解析成 `/root/ComfyUI/custom_nodes` → **[5/5] 工作流拷贝静默失败**（装完发现工作流目录是空的）。
   已修：脚本开头（任何 `cd` 之前）用绝对路径计算 `SCRIPT_DIR/REPO_DIR`。
2. **`download.py` 把没下完的文件当成已完成**
   文件是预先 `truncate` 到全尺寸的，所以"大小相同就跳过"的判断会把**中断的文件误判为完成**
   （实测：VAE 剩 63MB 卡住 → 重启脚本直接跳过 → 拿到一个残缺 VAE，静默损坏）。
   已修：增加 `path + ".done"` 完成标记 + 残留分片 `*.p*` 检查，未下完会打印 `[未完成]` 并允许续传。

## 五、远程运维小坑（租卡跑的话一定会碰）

- **`pkill -f download.py` 会杀掉自己**：远程执行时你自己的 `bash -c` 命令行里也含这个字面量。
  正解：按端口找进程（`ss -ltnp | grep ':8188'`），或写成 `[d]ownload.py` 这种自避正则。
- **中文输出乱码**：远程命令前加 `LC_ALL=C`，或把输出重定向到文件再取回。
- **长任务必须后台跑**：前台 SSH 命令超过约 120 秒会被切断（安装/下载一律后台 + 轮询日志）。
- **大文件传输必须校验**：曾出现 scp 截断（本地 14,811,136 vs 远端 15,329,995），
  用 `md5sum` 或字节数比对，别只看"传输完成"。
- **别用第三方"一键整合包"镜像测性能**：测出来的是那个镜像的性能，不是本仓库的。用基础 PyTorch 镜像。

## 六、本次实测数据（无 SLA，4090-48G）

| 分辨率 | 步数 | 端到端 | 每步 | 显存峰值 |
|---|---|---|---|---|
| 832×480（0.4MP） | 4 | **54.0 s** | ≈8 s | 48.5 GB |
| 1024×576（0.6MP） | 4 | **84.1 s** | ≈16.5 s | 48.2 GB |
| 1024×576（0.6MP） | 6 | **117.1 s**（冷启） | 15.35 s | 48.2 GB |
| 1344×768（0.98MP） | 6 | **243.1 s** | ≈37 s | 48.1 GB |

固定同一张图 + 同一段提示词，seed=42，图生视频 124 帧（5.17 秒）。

> ⚠️ 测试卡是 **4090-48G（显存魔改版）**：**GPU 核心与标准 4090 相同，速度数据可直接对比**；
> 但**显存结论不能套到 24GB 卡上**——24GB 必须走 offload，会明显更慢。
> 另外冷启动额外 20~25 秒（要加载 26GB 编码器 + 21GB 主模型）。
